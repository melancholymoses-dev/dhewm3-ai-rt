   + phase CPU (cpu.total .502 + cpu.raster .667) + other .330 = 1.709.  0.002 ms apart.

4. Resolution scaling matches the known floor. 0.667 -> 1.000 is 2.25x the pixels but

   This is arc 2's floor (docs/plans/completed/20260918_fsr_upscaling.md s12) showing up
   as an independent confirmation rather than an assumption.

Findings
--------
F2 confirmed, and worse than the audit assumed. frame.upload p50 0.153 but max 7.3-9.9 ms
in EVERY one of the 17 windows. Roughly one frame in 30 eats a 7-10 ms blocking upload
*while standing still*, so it is not confined to the "heavy frames" the audit described.
This is now the top CPU item and it promotes A2 above everything else.

frame.other max 11.8 against a p95 of 0.400. One frame per window has ~12 ms of
unattributed backend time. Not explained by this capture: the waits group was off, so
whatever blocks is not yet attributed. Needs a re-run with groups 15 and a spike line.

Raster exceeds RT at 1:1 (6.07 vs 4.27) and Interactions alone is 5.76 — larger than every
RT pass combined. Says nothing about arc 8a yet: this spot reads Shadows 0.168 because the
entrance has almost no shadow-casting lights, so the serial-dispatch claim still needs the
MC2 corner.

Dead screen-space paths show as 0.001: GI, GITemporal, Vol, VolTemporal, VolBilateral.
Confirms arc 8 phases 3 and 4 have nothing live to delete.

Bug found by this capture
-------------------------
Window 1 read p50 2.563 / p95 4.287 while windows 2-18 all read p50 ~4.27. The 2.563 is the
0.667-scale value from before the setting changed: a partial window survived profiling being
toggled off, because PushFrame is unreachable while off and nothing cleared s_windowCount.
Fixed in VK_Prof_BeginFrameSlot (discard the partial window on an off->on transition or a
window-size change). Treat the first window after any cvar change in earlier logs as suspect.

Capture 2: Communications fire, 4171 frames, full CSV (base/a0.csv)
-------------------------------------------------------------------
Same machine. Many lights, shadows, particles. The area that chugs on the 2600X/9070XT.
It does NOT chug here: gpu.total p50 4.79, frame.backend p50 1.72.

ARTIFACT FOUND FIRST, everything below is after discounting it.
frame.other p99 16.0 / max 20.9 is the profiler printing its own console block. 137 of the
139 frames with other > 8 ms are exactly 30 frames apart = the window-close frame. ~40
common->Printf calls cost 15-20 ms. Now measured as frame.profilePrint and counted in
accounted. This also explains capture 1's "12 ms unattributed" (one frame per window).
Rule: treat any periodic spike at the window interval as the tool, not the engine.

What the capture settles
  Shadows own RT here: gpu.Shadows p50 2.36 / p95 4.11 / max 6.75, half of gpu.total 4.79.
    gpu.Interactions p50 is only 0.080 (p95 2.56), so the batch path is working in this
    area and the serial dispatch of arc 8a is location-specific — it needs >7 shadow
    lights in view. The MC2 corner remains the only place that reproduces it.
  F1 confirmed with numbers: ring.idxKB p50 276 / p95 567 / max 717 per frame, ring.vertKB
    p50 39 / max 392, ring.draws p50 321 / p95 949. Index data is re-copied every frame
    because Vulkan forces r_useIndexBuffers 0.
  F2 cause confirmed: upload.staticBlocks p50 13 / p95 35 / max 90 per frame, standing
    still. upload.KB p50 173 / max 416. frame.upload p99 6.6 / max 11.3.
  F3 has no evidence here: midframe.imageLoads is zero across all 4171 frames, and every
    wait tag except uploadFlush (max 1.46 ms) is zero. The lazy-image-load half of A2 is
    not what hitches this area. Drop it unless another section shows it.
  A4 / F12 have no evidence: mem.rssMB 228-276 flat, virtMem ~7 MB, VRAM 2352 of 15504.
    No residency or VRAM pressure to fix.
  blas.rebuilds p50 0 / max 9 - live play refits in place, as expected.
  One genuine outlier, n=1: frame 8181 spent 21.6 ms in cpu.ShaderPasses with
    upload.flushes=1 and wait.uploadFlush 1.46 ms. Not periodic. Worth one look, not a stage.

Not answerable by more logging
  Why this area chugs on the 2600X/9070XT and not here. That needs the same CSV captured on
  that machine. No additional counters would help.
